# Kinshore Bay — локальный ресепшен

Локальная CRM на Django хранит корпуса, категории, апартаменты и демонстрационные заявки в SQLite. Серверные тесты, включая одновременные подтверждения, также проходят на PostgreSQL.

Заявки и статусы здесь вымышленные: это не реальные бронирования или платежи. Личные данные гостей не собираются.

## Открыть экран смены

После установки зависимостей из корня проекта выполните в PowerShell:

```powershell
& 'crm/.venv/Scripts/python.exe' crm/manage.py migrate
& 'crm/.venv/Scripts/python.exe' crm/manage.py seed_demo --shift
& 'crm/.venv/Scripts/python.exe' crm/manage.py create_reception_user receptionist
& 'crm/.venv/Scripts/python.exe' crm/manage.py runserver 127.0.0.1:8000
```

Команда создания аккаунта запрашивает пароль в терминале. При следующих запусках используйте созданный аккаунт. Войдите на [экране ресепшена](http://127.0.0.1:8000/reception/). **Today** показывает заезды, выезды и новые заявки. Введите номер для поиска, откройте заявку и выберите свободный апартамент её категории. **Occupancy** показывает семь ночей с указанной даты.

Команда `seed_demo --shift` добавляет синтетический заезд, выезд и новую заявку с конфликтом на текущую дату UTC. Чтобы увидеть конфликт, откройте заявку `conflict-ГГГГММДД` из раздела **New requests**. Повторный запуск сохраняет существующие записи.

Для совместного показа откройте [гостевой сайт](http://127.0.0.1:8000/site/index.html) в отдельном профиле или приватном окне. Отправьте заявку, найдите её по номеру на ресепшене и подтвердите. Нажмите **Refresh my requests** в гостевом **My stay**. После отмены статус обновится при повторной загрузке, а даты освободятся в календаре.

## Посмотреть данные

Из корня проекта в PowerShell:

```powershell
& 'crm/.venv/Scripts/python.exe' crm/manage.py show_demo
```

Команда `seed_demo` наполняет локальную SQLite синтетическим инвентарём из 15 апартаментов в пяти корпусах. База создаётся в `crm/local-demo.sqlite3` и исключена из Git. Для первого запуска:

```powershell
python -m venv crm/.venv
& 'crm/.venv/Scripts/python.exe' -m pip install -r crm/requirements.txt
& 'crm/.venv/Scripts/python.exe' crm/manage.py migrate
& 'crm/.venv/Scripts/python.exe' crm/manage.py seed_demo
& 'crm/.venv/Scripts/python.exe' crm/manage.py setup_demo_roles
& 'crm/.venv/Scripts/python.exe' crm/manage.py show_demo
```

Повторный `seed_demo` сохраняет существующие записи и статусы; категории и цены при первом заполнении берутся из `content/en.json`. Последующие изменения каталога не синхронизируются с базой автоматически.

## Правила демо-заявок

Внутренние статусы: `requested → confirmed → checked_in → checked_out`. Статусы `requested` и `confirmed` также могут перейти в `cancelled`. Сервис проверяет корректность дат, срок до 90 ночей, вместимость и пересечение с подтверждёнными демо-проживаниями; заезд в день предыдущего выезда допускается. Заявка фиксирует цену за ночь на момент создания.

При подтверждении PostgreSQL блокирует выбранный апартамент до завершения транзакции. Если даты заняты, сотрудник получает конфликт и может выбрать другой доступный апартамент той же категории. Смена статуса, назначение апартамента и запись истории фиксируются одной транзакцией. История содержит автора, время и переход. Изменения, сделанные до миграции журнала, в нём отсутствуют. Для одновременной работы нескольких сотрудников используйте PostgreSQL.

## Роли в локальной модели

Созданы две группы Django:

- `kinshore_reception`: просмотр апартаментов и заявок, создание заявки и изменение её статуса.
- `kinshore_owner`: просмотр апартаментов и заявок и право на будущую аналитику. Изменение заявок этой роли не предоставлено.

Экраны используют сеанс Django и серверные проверки разрешений. Для изменения статуса нужен POST с CSRF-токеном. Django-superuser имеет все права. Право на аналитику зарезервировано для будущего экрана.

Повторный `setup_demo_roles` проверяет группы и не перезаписывает их при расхождении. `seed_demo` и `show_demo` — доверенные локальные команды для владельца компьютера и не проверяют роль. Прямая работа с ORM или базой тоже не является защищённым пользовательским интерфейсом. При создании API и UI нужно обязательно использовать проверки доступа на сервере, а не только скрывать кнопки.

Посмотреть права локальных групп:

```powershell
& 'crm/.venv/Scripts/python.exe' crm/manage.py show_demo_roles
```

## Локальный прототип приёма заявок

Подготовлен машинный endpoint `POST /api/internal/demo-requests/`. Он **выключен по умолчанию**: настройки служебного доступа и аккаунт не созданы. В боте подготовлен вызывающий клиент, который активируется только при настройке адреса и отдельного секрета; без этого данные не отправляются.

Для будущего подключения предусмотрены `KINSHORE_CRM_TOKEN` и `KINSHORE_CRM_USER` в окружении процесса сервера. Нужен отдельный случайный секрет длиной 32–256 символов из букв, цифр, `_` и `-`; это не токен Telegram. Указанный пользователь должен быть активным, без пароля, без административных прав и иметь только `reception.add_stayrequest`. Если конфигурации нет или она не соответствует правилам, endpoint отвечает `503`; неверный Bearer-токен получает `401`. Данные секретов не помещать в репозиторий, логи или чат.

Запрос принимает `Authorization: Bearer …`, UUID в заголовке `Idempotency-Key` и JSON с апартаментом или категорией, датами и количеством гостей:

```json
{"apartment_code":"A-101","checkin":"2030-06-10","checkout":"2030-06-14","guests":2}
```

Вместо `apartment_code` можно передать `category_id` (например, `"one"`), но не оба поля сразу. При выборе категории CRM назначает подходящий свободный демо-апартамент. Поле `nightly_cents` можно передать, чтобы проверить цену перед созданием заявки. Этим вариантом пользуется подготовленный клиент бота.

Успешное создание возвращает `201` и демонстрационный номер заявки, повтор того же запроса с тем же ключом — `200` без создания дубликата; другой запрос с уже использованным ключом — `409`. Проверяются формат дат, вместимость, срок проживания и существование апартамента. Никаких контактных данных или подтверждения реального бронирования этот endpoint не принимает.

Интеграционный тест использует код бота и Django с подменённым транспортом. Он проверяет права и повтор после потери ответа. Настройки `crm/config/settings.py` предназначены для loopback-превью. На VPS бот использует отдельный профиль развёртывания. [Инструкция для VPS](../deploy/README.md#telegram-bot)

## Проверка

```powershell
& 'crm/.venv/Scripts/python.exe' crm/manage.py check
& 'crm/.venv/Scripts/python.exe' crm/manage.py test reception
```

Конкурентный тест использует два отдельных соединения и допускает одно подтверждение на последний апартамент. Для запуска на выделенном тестовом PostgreSQL задайте `PGHOST`, `PGPORT`, `PGUSER` и при необходимости `PGDATABASE`. У роли должно быть право создавать тестовую БД. Для аутентификации можно использовать `PGPASSFILE`.

```powershell
& 'crm/.venv/Scripts/python.exe' -m pip install -r requirements-dev.txt
& 'crm/.venv/Scripts/python.exe' crm/manage.py test reception --settings=config.postgres_tests
```

Для проверки через браузер установите Playwright и Chromium в то же окружение. При наличии Edge или Chrome можно указать путь к его исполняемому файлу в `KINSHORE_BROWSER`.

```powershell
& 'crm/.venv/Scripts/python.exe' -m pip install -r requirements-dev.txt
& 'crm/.venv/Scripts/python.exe' -m playwright install chromium
& 'crm/.venv/Scripts/python.exe' crm/manage.py test reception.browser_desk
```

Статусы отражают действия сотрудника. Смену статуса по времени заезда или выезда должен инициировать сотрудник.

## Гостевые заявки из браузера

GET /api/guest/quotes/ возвращает категории с доступными демо-апартаментами, цену за ночь и итог в центах. My stay получает список по текущему сеансу через GET /api/guest/stays/. POST туда же создаёт заявку с проверкой CSRF, цены и доступности. Одна и та же категория, даты и число гостей в рамках сеанса соответствуют одной заявке. При подтверждении сотрудником место ещё раз проверяется на пересечение. Проверки этапа 3 выполнены на SQLite.

## Клубная прогулка

После миграции команда `seed_demo` создаёт субботние сеансы Pine & Shore Walk. На экране **Walks** выберите дату, чтобы увидеть остаток и список участников по заявкам. Ресепшен может отменить прогулку до начала, тогда статус появится у гостя в **My stay**. Сценарий браузерной проверки ресепшена включает запись двоих на последние места и их освобождение. Тест PostgreSQL проверяет одновременную запись на последнее место.

В деталях заявки Reception видит число детей, питомца и приезд на автомобиле. Отсутствующие ответы показываются как **Not provided**. Перед подтверждением заявки с питомцем проверьте размещение. В разделе **Grill pergolas** выберите дату, введите номер подтверждённого проживания в свободный слот и нажмите **Reserve**. **Release table** освобождает будущее время. Для этой версии примените миграцию `0007_arrival_details_and_grill_booking` обычной командой `migrate`.
